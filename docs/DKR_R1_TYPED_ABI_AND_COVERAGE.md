# DKR-R1: universal PTX loading and typed ABI

## Integration base and evidence boundary

- Integration branch: `haricot/mistral.rs:dynamic-kernel-runtime`.
- Candle source: `haricot/candle:cuda_legacy`, exact Git revision `d99f6d77e507688bd9e4b654fbe20ac9e18238fc`, `candle-*` version `0.11.1`.
- `Cargo.toml` and `Cargo.lock` must agree. The lock is regenerated by Cargo; it is not hand-edited.
- The earlier F32 SM61 evidence (`provider_f32_inference`, binary SHA256 `6545617b113031f2d9989fd596631e994b38abc5ac79cf9c5f2765cd955abbf7`) qualifies only the **previous** Candle revision `9cba2e898af3d25a89257f1f2ec5acece0404dcb`. It does not qualify the new pin or this DKR-R1 ABI.
- No NVCC toolchain override or obsolete `CUDA_COMPUTE_CAP` / `NVCC_CCBIN` variables belong in this workflow. SM61 compilation remains single-architecture and cached by content identity.

## R1 implementation contract

The new `mistralrs-kernel-runtime::universal` module has **no ASD dependency**. It exposes:

1. `DKR-KERNEL-MODULE-V1` / `dkr.typed.v1`: a versioned PTX module manifest whose operation identity, implementation ID, entry, SHA256, target and supported compute capabilities are explicit.
2. An ordered signature of *tensor* and *scalar* parameters. Tensors declare element type, rank, and read/write usage; launch requests must provide matching types, contiguous zero-offset layout, nonzero shapes and an aggregate byte budget.
3. Content-addressed artifact verification with bounded size, safe relative paths, symlink-escape rejection, PTX address size, architecture and `.entry` argument-width verification. The immutable in-memory verified package does not reread artifacts during selection.
4. `KernelCatalog::load` and `discover` for an external package directory, plus `resolve` to select the highest compatible architecture target for the operation and typed arguments. Multiple equally compatible implementations at the same target are refused as ambiguous. `select` remains available to pin one implementation family explicitly. There is no tuner, score-driven selection or silent CPU fallback.
5. Under the `cuda` feature, `universal_cuda::PreparedKernel::load` reuses Candle's CUDA module cache and provides a checked launch configuration. The actual CUDA launch is **unsafe and adapter-owned**, because the ABI metadata alone cannot prove that borrowed GPU buffers match the launch arguments or that the PTX is memory-safe.

The previous `mistral.linear.f32.v1` profile/session path remains untouched and is not implicitly migrated. The new package proof in [`kernel-packages/`](../kernel-packages/README.md) has two PTX variants implementing the same vector operation and an optional CUDA execution example that detects the device. It does not establish an end-to-end GPU model inference proof.

### Package example

```json
{
  "schema": "DKR-KERNEL-MODULE-V1",
  "abi": "dkr.typed.v1",
  "operation": "tensor.elementwise.scale.v1",
  "implementation_id": "pascal.f32.scalar",
  "artifact": "fused.ptx",
  "sha256": "<64 hexadecimal characters; SHA256 of fused.ptx>",
  "entry": "fused",
  "target_cc": 61,
  "min_cc": 61,
  "max_cc": 61,
  "block": [128, 1, 1],
  "shared_mem_bytes": 0,
  "arguments": [
    { "kind": "tensor", "name": "input", "dtype": "f32", "rank": 2, "access": "read" },
    { "kind": "scalar", "name": "alpha", "dtype": "f32" },
    { "kind": "tensor", "name": "output", "dtype": "f32", "rank": 2, "access": "write" }
  ]
}
```

PTX is the supported package format in R1. CUBIN/fatbin, runtime NVRTC compilation, native shared-library/FFI providers, strided/offset tensor arguments, GPU synchronization graphs and executable device memory interfaces remain explicit future ABI extensions. SHA256 is an integrity check, **not** a sandbox or a trusted-code signature. Only vetted packages may reach a CUDA launch.

## Complete source-family inventory, not a false completion claim

The audit covers every checked-in `.cu` compilation unit in the integration repository and optionally the exact Candle checkout. It also enumerates every method of Candle's `BackendStorage` and `BackendDevice` traits, including operations **without** a dedicated `.cu` file. The audit fails on a new unclassified source or backend method. Classification is not the same as a working dynamic adapter.

```bash
python3 tools/dkr_r1_inventory.py --candle-dir /path/to/candle-at-d99f6d7
cargo test -p mistralrs-kernel-runtime --no-default-features --locked
cargo fmt --package mistralrs-kernel-runtime -- --check
```

`--candle-dir` must point to a checkout of the pinned `cuda_legacy` revision. On the audited revision: **196 CUDA compilation units, 24 mapped source categories, 44 Candle backend methods, 0 unclassified** (includes 53 FlashAttention SM80-only units, 2 preserved POC units and 28 Candle source units). This is a source and backend-API classification gate, **not** 196 runtime-ready packages.

## Progression before Extended or ASD

### DKR-R1.1 external MoE boundary (experimental)

The optional `mistralrs-core/dkr-moe` feature routes `moe_gemm` through the
generic typed catalogue and CUDA launcher. Its old implementation is preserved
in `moe_legacy.rs` as the isolated numeric baseline. All new architecture
package source is under `kernel-packages/cuda/moe/`; `build.py --cc 61` compiles
the F16/BF16 reference provider independently of Cargo and writes verified PTX
manifests under `kernel-packages/build/cuda` (ignored by Git). The input and
output contracts stay stable across architectures, and the dynamic path has no
Pascal/WMMA branches or compile-time architecture predicates.

The reference provider deliberately uses scalar math, not promoted HFMA2
optimization. It has no silent fallback to the statically linked MoE. Its
separately built PTX and typed CUDA adapter require actual SM61 numeric testing
before qualification or merging. The external catalogue is loaded once per
process; prepared CUDA functions are cached for each typed request and device,
with a bounded 128-entry cache. Warm requests do not repeat device capability
queries, provider selection, PTX verification or module loading. Packages may
be replaced without rebuilding Rust, then the process must be restarted to
discover the new versions. The remaining tensor validation, launch-argument
construction and cache lookup have not been proven zero-cost; CPU/GPU latency
parity requires an A1/B/A2 comparison using the same underlying kernel. This
step does not migrate the remaining CUDA source families or remove build-time
specialization elsewhere.

### DKR-R1.3 external indexed-copy boundary (experimental)

`dkr-indexed-copy` adds a second production adapter on the same shared CUDA
execution cache. This covers a distinct operation family: in-place indexed row
copying for the KV cache. The external module has two bit-preserving PTX entry
points and three typed manifests for F16, BF16 and F32. The single-architecture
builder generates the packages separately from Cargo and reuses the unchanged
output. The static CUDA source is excluded when the feature is enabled.

The optional path preserves storage offsets and rejects invalid destination
indices in the device kernel. A combined ignored GPU test filter `dkr_` runs
MoE and indexed-copy tests from one compiled `mistralrs-core` binary. This is
not a claim that the other source families are already dynamic or that GPU
performance is unchanged.

### DKR-R1.4 prevalidated launch plans

`PrevalidatedLaunchPlan` retains the CUDA function and verified launch
configuration after one typed admission per signature and device. The MoE and
indexed-copy adapters use bounded thread-local caches with fixed-size keys.
Warm dispatch does not recreate the typed request, lock the shared module
cache, query device capability, or rerun manifest admission. The keyed lookup,
tensor validation, pointer preparation and CUDA submission still have a cost;
zero latency regression is a final qualification target, not a measured result.

The original checked `with_verified_launch` API remains available to adapters
that have not adopted a reusable plan. The prevalidated launch API is unsafe:
its caller must maintain the previously admitted device, tensor type/layout and
launch parameter invariants on each replay. The hot-path cache unit test uses
a scalar mock plan and does not launch a GPU kernel, although the feature-enabled
crate still has CUDA build dependencies. Real CUDA tests remain intentionally
ignored until the single final functional and A1/B/A2 performance campaign.

CUDA Graph capture and replay are a separate final-stage extension. They may
reduce sequence-level launch overhead, but no core DKR operation requires them.

### DKR-R1.5 external fused gated-add provider

`dkr-gated-add` moves the sigmoid-gated residual addition path to an external
four-entry PTX package, retaining the same F16/BF16/F32 rounding operations as
the historical CUDA source. The F32 row-tiled variant remains selected by
column width; no architecture-specific conditional is added to generic Rust.
The existing broadcast/layout fallback is preserved, and the provider uses
R1.4 prevalidated launch plans. Its PTX is built once per requested compute
capability, then referenced by four typed manifests.

`kernel-packages/cuda/build_all.py --cc 61` is the single batch entry point for
the migrated package families. Each builder retains its content-based reuse
cache. The final GPU campaign will include F16/BF16/F32 numeric parity, the
existing exact-rounding and CUDA Graph replay cases, and separate host/GPU
latency measurements. No GPU compilation or qualification is claimed for this
increment, and the rest of the source inventory remains pending migration.

### DKR-R1.6 external reductions and normalization

`mistralrs-quant/dkr-reduce-norm`, exposed by
`mistralrs-core/dkr-reduce-norm`, migrates two actual CUDA consumers through
the same versioned ABI and thread-local prevalidated launch-plan strategy:

- MoE weighted reduction of `[tokens, topk, hidden]` by F32 routing weights,
  preserving F32 multiply/add rounding order and all nine combinations of
  F16, BF16 and F32 input/output types.
- Sink-aware attention softmax used by GPT-OSS, including the sink in the
  denominator without emitting a sink probability. Five width buckets retain
  the legacy CUDA block sizes (64, 128, 256, 512 and 1024 threads), across
  F16/BF16/F32. The optional attention mask is still applied upstream.

`kernel-packages/cuda/reduce-norm/build.py` compiles one PTX module per
requested architecture, then writes 24 typed manifests for its entry points
and softmax launch-size variants. Opting in excludes `weighted_reduce.cu`
and the old softmax kernel section in `ops.cu` from the quant CUDA archive.
Unopted-in builds retain their old CUDA FFI implementations; CPU and Metal
paths are unchanged.

This tranche does **not** migrate Candle's general RMSNorm/LayerNorm,
FP8-fused RMS normalization, generic sum/max reductions or other attention
softmax paths. They require separate ABI and numerical audits. R1.6 adds
ignored GPU parity/cache tests, but does not claim SM61 qualification or
latency parity until the final combined test and paired A1/B/A2 benchmark.

1. **R1a, closed**: exact Candle pin/lock regeneration; independent typed manifest, catalogue and artifact loading; host-only tests and source classification.
2. **R1b, required**: typed CUDA tensor launch adapters, architecture-feature negotiation and explicit preallocation memory budget (especially packed FP8/FP4 and MoE); negative tests for invalid pointer/order/context, fallback absence and numerical parity.
3. **R1c, required**: migrate operation families incrementally from Candle's `cuda_legacy` and Mistral's CUDA launch points; keep unsupported SM61 MMA/FlashAttention variants behind honest capability rejection and choose qualified SIMT alternatives.
4. **R1d, required**: GTX 1080 Max-Q SM61 end-to-end proof with clean exact locks, one build per changed binary identity, reused caches, `cargo nextest`, per-operation numeric parity and model prefill/decode evidence; record complete new binary and PTX hashes.
5. **Only then**: optional ASD auto-selection and promotion policies. The runtime and typed ABI do not depend on ASD, and Extended is not the source branch for DKR work.

No unqualified source family is reported as GPU-ready merely because it appears in the inventory.
